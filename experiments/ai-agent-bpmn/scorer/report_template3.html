AI Agent BPMN Bake-off

Three ways to build the Camunda "AI Agent Chat With Tools" tutorial process from a plain-language spec: a Python generator, a bpmn-js-cli fork extended for Camunda 8, and hand-written XML with the camunda-bpmn skill. Each method ran twice in isolation, and each run was scored on cost, closeness to the canonical file, and time until lint and the tutorial's own test suite passed.

10 trials, all passed the hard gateFork: private repoNothing merged into camunda/skillsRan on c8ctl v4.0.0; current is v4.5.0

Result

Hard gate10 of 10 pass

Every trial ended with 0 lint errors and 6 of 6 CPT scenarios green. Eight passed on their first gate attempt.

Closeness87 to 89 / 100

Hand-written XML scored highest (mean 89.0). Python and the extended CLI tied at about 87, a gap of 2 points.

Cost124k to 133k tokens

Python was cheapest on average. The gap between the cheapest and dearest method is about 7%.

Time2.7 to 3.2 min

Hand-written and Python averaged under 3 minutes of active time. The extended CLI averaged 3.2 minutes.

Update, 16 October. A third CLI round (cli5, cli6) tried built-in help, a filterable template listing, a documented option list and named flow ids. Calls and time fell slightly, within noise. See the timeline section for the phase breakdown and the follow-up.

On this task no method is clearly better. With two trials each, the differences sit inside run-to-run noise. Choose on other grounds: what the method gets right by construction, and what it leaves to the author.

One difference that looked real was a tooling artifact. The trials ran on c8ctl v4.0.0, which drops zeebe:agentDefinition when applying the AI Agent template, so only the CLI trials kept it. That was already fixed in camunda/c8ctl#574 and ships in v4.5.0. With the element restored, each Python and hand-written run gains 0.3 points (means 87.4 and 89.3), so the ranking holds. The difference that does hold is layout: the CLI scored lowest of the three.

Why did the CLI spend longer thinking?

Short answer: more steps in some runs, not slower steps. The transcripts redact the reasoning text, so what an agent reasoned about can only be read from its tool calls and its own report. "Fork reads" counts reads of the fork's README or source, "template lookups" includes filtering the output, and "composing" is model time spent writing tool calls other than file writes.

  1. Steps were not slower. Model time per call was 5.0 to 8.0 seconds in all 10 runs. The extra time is more calls.
  2. The CLI needed orientation the others did not. Every CLI run read the fork's README or source (1 to 6 calls), and no Python or hand-written run read any tool source. The README lists commands but not their options, and in v1 and v2 help printed command names only. Every CLI run also rendered its diagram to check layout (1 to 3 times), which no other run did. Both v2 runs filtered a template property dump of about 150 entries (2 and 3 calls).
  3. One run drove the average. cli3 made 21 calls, took 146 seconds and spent 18 seconds in hidden reasoning, the fastest of all 10 runs. cli4 made 35 calls, took 238 seconds, spent 58 seconds in hidden reasoning and made 7 write or edit calls on its script. Its own report names the cause: resizing the sub-process shifted everything else, so it looked up connection ids by position, renamed the flows, and routed the "No" loop with explicit waypoints. That is coordinate and id bookkeeping.
  4. Ideas to cut it, now tested once. Print each command's options from help, make template-props filterable and condensed, document the options in the README, and let append and connect name the flow they create. The follow-up round below tried all four (rows cli5 and cli6).

Did built-in help cut the cost? (CLI v3)

I made those four changes to the fork (commit e785e53 on the private repo) and ran two more trials with the same briefs, cli5 and cli6. They appear as "Extended CLI (v3, with help)" in every chart and table. Two trials per round cannot separate a small effect from noise, so read the first point first.

  1. Calls and time moved a little, inside the noise. Mean tool calls went from 28 to 26.5, tokens from 130,882 to 124,347 (5% fewer) and active time from 192 s to 173 s (10% less). The two v2 trials ranged from 21 to 35 calls and 146 to 238 s, and cli3 alone was faster than both v3 runs.
  2. Template lookups halved. v2 runs made 8 lookup or filter calls each; cli5 made 5 and cli6 made 3. cli5 asked help for command arguments and used the condensed property list.
  3. Flow-id lookups are gone. Both v3 runs named their flows with the new argument (6 times each) and made one elements() call, which was for something else.
  4. The orientation cost moved, it did not vanish. README or source reads were 5 and 1, against 4 and 2 in v2. Both agents still hit a stray start event that replace leaves inside an ad-hoc sub-process, and neither could print from model.js. cli5 needed 3 gate attempts after two lint errors and worked around a shell path restriction through a symlink, which probably cost it a few calls.
  5. Closeness was about 89 in both runs (cli5 89.8, cli6 88.5), against 87.3 and 86.9 for v2. That is inside the spread seen between trials of the same version.

Method: each gap between two transcript events belongs to one phase. The gap before a Write or Edit is creating (or fixing, once a lint or test has run). The gap before any other model output is thinking. The gap before a tool result is that tool running: lookups, lint, the test script, or running the generator, the CLI or c8ctl element-template apply. A command that rebuilds and lints in one line counts as linting. Misc shell housekeeping (under 3 s per run) is folded into looking up. The phase times add up to each agent's wall-clock time.

Has the extended CLI plateaued?

This data cannot say. Each version has two trials, and the gap between trials inside a version is as large as the change between versions. Here is what the two rounds do show.

{{PLATEAU_ROWS}}
Mean of 2 trialsv1v2ChangeScripted runGap left
  1. The closeness gain is inside the noise. Closeness rose 1.8 points, but the two v1 trials differ by 2.6 and the two v2 trials by 0.4. Active time was flat (194 to 192 s) while the v2 trials differ by 92 s, and the 8% token drop sits inside the 14k spread between the two v2 trials.
  2. Where the points moved. Layout rose 1.5, which is what the v2 fixes were aimed at. Configuration rose 0.9 with no fix aimed at it. Structure fell 0.6 because cli4 never set the "AI Agent" label, which was the agent's omission and not a tool limit.
  3. The remaining gap is a floor set by the stop rule, not by the tool. The briefs told agents to stop once lint and tests passed. The "scripted run" is my own acceptance script, which reached 93.8 and passed the same gate. I wrote it with the canonical file's layout in view, so treat it as an upper bound and not a fair target. About 2.4 points of its configuration lead come from forcing ignoreNullValues onto the GET tools, which the template does not offer and the agents correctly skipped.
  4. To test for a plateau, run more trials per version, and add a third condition where agents keep improving closeness after the gate passes. Without that, a flat score would mean the agents stopped, not that the tool did.

Tooling findings

These came up during the experiment and matter beyond it. Each is labelled with how it was established.

  1. The installed c8ctl was out of date. v4.0.0 dropped zeebe:agentDefinition on element-template apply and bpmn format. camunda/c8ctl#574 fixed this on 17 September 2026, and v4.5.0 includes it. Re-tested on the same input: v4.0.0 drops the element and v4.5.0 keeps it. The skill's prerequisite floor (c8ctl 3.2.0 or later) does not guard against this.
  2. Lint passes an attribute that Zeebe rejects at deploy. An unprefixed executionPlatformVersion on bpmn:definitions lints clean, and every CPT scenario then fails on an XSD error. Verified during fork acceptance. The CPT gate caught it, not lint.
  3. The AI Agent template's result variable is not settable by name. All 4 Python and hand trials tried resultVariable with c8ctl and were rejected, because the binding is keyed by its source =agent. In the CLI, setting it wrote a stray empty input. One agent also reported that c8ctl's --set name=value cannot express a key that starts with =; that part is the agent's report and has not been verified separately.
  4. v4.0.0 also linted 8.10 files with the 8.9 ruleset and flagged 3 deprecated-secret warnings. v4.5.0 lints hand2's file with no fallback and no warnings.
  5. The fork's first version had three layout defects, found by the CLI trials: replace left sub-processes collapsed, annotate ignored width and height, and there was no way to route a connection. All three are fixed and tested in v2. The v1 trials averaged 85.3 closeness against 87.1 for v2.
  6. Sandbox friction was equal across methods. Every trial reported the worktree sandbox refusing compound shell commands and heredocs, and worked around it with absolute paths and the Write tool.

Setup

  1. Baseline. A plain-language spec derived from the tutorial's canonical BPMN. It states behaviour in prose but quotes literal values: prompts, URLs, FEEL conditions, element IDs the tests select, and documentation text.
  2. Methods. Python: a generator script; the XML may not be hand-edited. Extended CLI: a command script run by the fork's headless runner; no XML edits or post-processing. Hand: Write and Edit only, following the camunda-bpmn skill. All methods could use c8ctl element-template apply, and all Python and hand trials did.
  3. Done gate. 0 lint errors from c8ctl bpmn lint (v4.0.0, the installed version), and the tutorial's CPT suite (6 scenarios, agent and tools mocked) green via Maven. Warnings allowed.
  4. Isolation. Each trial had its own worktree and run directory. The canonical file, the tutorial sources and the scorer were moved out of the shared area, CPT run copies were deleted after each run, and briefs forbade fetching the tutorial. This was enforced by instruction, not by permissions.

Metrics and caveats

  1. Closeness (0 to 100). F1 over facts extracted from both files, so missing and invented facts both cost points. Weights: structure 25, configuration 50, annotations 10, layout 15. Validated: the canonical scores 100 against itself, whitespace-only edits score 100, and single mutations lose points. FEEL literals such as =20 and 20 count as equal, because the canonical mixes both.
  2. Cost. Subagent tokens reported by the harness for the whole trial.
  3. Time. Agent wall-clock minus queue time. CPT runs were serialized to protect another stack running on this machine.
  4. Sample. Two trials per method, one task, one model, so there is no variance estimate. As a judgement call rather than a measurement, read differences under about 3 closeness points or 10% tokens as noise.
  5. Not counted. Building the fork was a one-time cost on the main thread and is not in the CLI numbers. It amounts to about 770 lines of command code plus a runner, 17 new tests, and two rounds of fixes.

The fork

The extension lives on branch camunda-executable of the private repo HanselIdes/bpmn-js-cli, a copy of bpmn-io/bpmn-js-cli 2.4.0. GitHub does not allow private forks of public repositories, so it is a private repo with upstream history rather than a fork. It adds 17 commands for Zeebe extensions, conditions, documentation, annotations, sizing, waypoints and element templates, plus a headless runner. Upstream command behaviour is unchanged, and all 33 tests and eslint pass.
