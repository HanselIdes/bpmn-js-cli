AI Agent BPMN Bake-off

Three ways to build the Camunda "AI Agent Chat With Tools" tutorial process from a plain-language spec: a Python generator, a bpmn-js-cli fork extended for Camunda 8, and hand-written XML with the camunda-bpmn skill. Each method ran twice in isolation, and each run was scored on cost, closeness to the canonical file, and time until lint and the tutorial's own test suite passed.

8 trials, all passed the hard gateFork: private repoNothing merged into camunda/skills

Result

Hard gate8 of 8 pass

Every trial ended with 0 lint errors and 6 of 6 CPT scenarios green. Seven passed on their first gate attempt.

Closeness87 to 89 / 100

Hand-written XML scored highest (mean 89.0). Python and the extended CLI tied at about 87, a gap of 2 points.

Cost124k to 133k tokens

Python was cheapest on average. The gap between the cheapest and dearest method is about 7%.

Time2.7 to 3.2 min

Hand-written and Python averaged under 3 minutes of active time. The extended CLI averaged 3.2 minutes.

On this task no method is clearly better. With two trials each, the differences sit inside run-to-run noise. Choose on other grounds: what the method gets right by construction, and what it leaves to the author.

Two of those grounds showed up clearly. The extended CLI is the only method that kept zeebe:agentDefinition, because c8ctl element-template apply silently drops it and every other trial used c8ctl for templates. The CLI's weak spot is layout, which scored lowest of the three methods.

Tooling findings

These came up during the experiment and matter beyond it. Each is labelled with how it was established.

  1. c8ctl drops zeebe:agentDefinition on element-template apply and on bpmn format. Verified: a format round-trip of the canonical file loses it, and all 4 apply-based trials lack it. CPT still passes because it mocks the agent job, so the runtime effect is unverified.
  2. Lint passes an attribute that Zeebe rejects at deploy. An unprefixed executionPlatformVersion on bpmn:definitions lints clean, and every CPT scenario then fails on an XSD error. Verified during fork acceptance. The CPT gate caught it, not lint.
  3. The AI Agent template's result variable is not settable by name. All 4 Python and hand trials tried resultVariable with c8ctl and were rejected, because the binding is keyed by its source =agent. In the CLI, setting it wrote a stray empty input. One agent also reported that c8ctl's --set name=value cannot express a key that starts with =; that part is the agent's report and has not been verified separately.
  4. c8ctl lints 8.10 files with the 8.9 ruleset, printing a fallback warning on every run.
  5. The fork's first version had three layout defects, found by the CLI trials: replace left sub-processes collapsed, annotate ignored width and height, and there was no way to route a connection. All three are fixed and tested in v2. The v1 trials averaged 85.3 closeness against 87.1 for v2.
  6. Sandbox friction was equal across methods. Every trial reported the worktree sandbox refusing compound shell commands and heredocs, and worked around it with absolute paths and the Write tool.

Setup

  1. Baseline. A plain-language spec derived from the tutorial's canonical BPMN. It states behaviour in prose but quotes literal values: prompts, URLs, FEEL conditions, element IDs the tests select, and documentation text.
  2. Methods. Python: a generator script; the XML may not be hand-edited. Extended CLI: a command script run by the fork's headless runner; no XML edits or post-processing. Hand: Write and Edit only, following the camunda-bpmn skill. All methods could use c8ctl element-template apply, and all Python and hand trials did.
  3. Done gate. 0 lint errors from c8ctl bpmn lint, and the tutorial's CPT suite (6 scenarios, agent and tools mocked) green via Maven. Warnings allowed.
  4. Isolation. Each trial had its own worktree and run directory. The canonical file, the tutorial sources and the scorer were moved out of the shared area, CPT run copies were deleted after each run, and briefs forbade fetching the tutorial. This was enforced by instruction, not by permissions.

Metrics and caveats

  1. Closeness (0 to 100). F1 over facts extracted from both files, so missing and invented facts both cost points. Weights: structure 25, configuration 50, annotations 10, layout 15. Validated: the canonical scores 100 against itself, whitespace-only edits score 100, and single mutations lose points. FEEL literals such as =20 and 20 count as equal, because the canonical mixes both.
  2. Cost. Subagent tokens reported by the harness for the whole trial.
  3. Time. Agent wall-clock minus queue time. CPT runs were serialized to protect another stack running on this machine.
  4. Sample. Two trials per method, one task, one model, so there is no variance estimate. As a judgement call rather than a measurement, read differences under about 3 closeness points or 10% tokens as noise.
  5. Not counted. Building the fork was a one-time cost on the main thread and is not in the CLI numbers. It amounts to about 770 lines of command code plus a runner, 17 new tests, and two rounds of fixes.

The fork

The extension lives on branch camunda-executable of the private repo HanselIdes/bpmn-js-cli, a copy of bpmn-io/bpmn-js-cli 2.4.0. GitHub does not allow private forks of public repositories, so it is a private repo with upstream history rather than a fork. It adds 17 commands for Zeebe extensions, conditions, documentation, annotations, sizing, waypoints and element templates, plus a headless runner. Upstream command behaviour is unchanged, and all 33 tests and eslint pass.
